# Application audit — 9 September 2026

Scope: source and requirements review, full existing test suite, and isolated in-memory Qt reproductions. No hardware commands, production data changes, or application fixes were made. This was not a visual audit on the gate PC.

Validation: `.venv\Scripts\python.exe -m pytest -q --tb=short` — **266 passed**. The initial sandbox run had 22 temporary-directory permission errors; the approved rerun passed. The default system Python lacks pytest; use the project virtual environment.

## Findings, in repair order

1. **High — simultaneous Entry windows silently overwrite visits.** `ui/admin_window.py:285` creates another independent portal on every click. `ui/pages/entry_portal.py:856` allocates IDs from that window's snapshot; `storage.py` upserts visits by ID. Reproduction: two portals opened from the same store both submitted `VIS-000141`; only the second vehicle remained in the database. Allocate IDs atomically in storage and reject conflicting inserts; also reuse a single portal per session.

2. **High — Reporter has administrative and barrier access.** `routing.py:39` routes Reporter into Admin, but `ui/admin_window.py:114` builds all pages without role checks. Reproduction: a Reporter session has Users, Settings, E-Tags, Door Controls, and a visible Entry button. Enforce permissions at both navigation and action boundaries; Reporter must remain a desk role without barrier access.

3. **High — signing out leaves child portals authenticated.** `ui/admin_window.py:285`, `:304`, and `:323`: portals are independent windows, are not closed during Admin logout, and their logout signals are not connected to the application's session teardown. Reproduction: an open portal remained visible with its original session after Admin signed out. Closing windows with the title-bar X also bypasses the explicit Logout methods. Centralize session teardown, close all related windows, and audit session termination once.

4. **High — operational screens use stale snapshots.** `main.py:71`, `ui/admin_window.py:316`, `ui/pages/exit_portal.py:71`, and `ui/pages/vms_operations.py:213`: only Dashboard receives updated visits after an Admin-launched submission. Reproduction: a newly persisted visit was absent from both an already-open Exit portal and VMS Operations. Reports also retain construction-time data; E-Tag Logs retain an old registry after add/block/renew/delete. Refresh from a shared application service and recheck current visit state when committing checkout, so stale windows cannot overwrite earlier checkout decisions.

5. **High — empty real datasets are replaced by demonstration data in pages.** `ui/pages/vms_operations.py:216` calls demo seeding even with an explicitly supplied empty repository. Reproduction: database visit count was zero while VMS displayed 140 visits; manual checkout can persist one of these fictional records. `ui/pages/etag_logs.py:39` also substitutes a demo registry when the real registry is empty, risking incorrect classification of subsequent readings. Keep demonstration data explicitly opt-in and outside normal page initialization.

6. **High — late OCR results can populate the next visitor.** `ui/pages/entry_portal.py:529`, `:692`, and `:816`: the asynchronous completion handler always writes into the current form. Submit and Next remain available during OCR, and clearing the form does not invalidate the pending result. A result for visitor A arriving after clear/submit will put A's identity and image into visitor B's form. Give each capture a form-generation token and discard stale completions without blocking manual entry. This finding is based on the callback paths, not a physical camera test.

7. **Medium — record changes lack audit events, and manual checkout stores the wrong operator.** Users, E-Tags, and Categories receive repositories but no shared audit sink (`ui/admin_window.py:116` onward). Their mutation paths save/delete without recording who changed the record. `ui/pages/vms_operations.py:329` hardcodes `operator="admin"`, so the visit/report identity can disagree with the real audit operator. Record mutations through the signed-in application service and use the session identity consistently.

8. **Medium — visit success events precede persistence.** Entry `submit()` (`ui/pages/entry_portal.py:873`) and Exit `submit()` (`ui/pages/exit_portal.py:502`) update in-memory state and append success/gate audit events before invoking the persistence callback. A failed visit save therefore leaves success audit records without the saved transaction; the exceptions have no recoverable UI path. Commit the visit and its decision audit consistently, then represent device attempts and failures accurately.

9. **Medium — the configured data directory does not relocate the database.** `main.py:47` always opens the database using default settings, before loading saved settings. Changing Data folder in Settings only changes configuration and the image path; subsequent startups still use the original database. Define a bootstrap configuration location and an explicit, verified relocation workflow, or clearly limit the setting to images until that exists.

## Remaining implementation gaps

- Entry and Exit PCs currently open local SQLite stores. There is no Entry-hosted LAN data service or ongoing synchronization; the second PC cannot yet operate against live Entry records. Workstation identity is also stored in the database, so simply sharing the same file is not a complete solution.
- Controller commands, polling, e-tag programming, persistent pending sync, and Dahua feeds remain unintegrated. Receipt byte generation and printer modules exist, but Entry submission still simulates printing. These are expected later-stage hardware work under the agreed sequence.
- Visit records only persist the CNIC image path; driver, ANPR overview, plate crop, and exit evidence need a storage model and review UI. Exit currently cannot show the required entry photographs for comparison.
- Backup execution, automatic image retention, and Windows startup/recovery services are not implemented; Settings exposes values only.
- Camera monitoring and real destination dictation remain unfinished. Deployment account/password setup remains necessary before live use.
- The handoff file is stale: Dashboard, Exit portal, and Settings persistence now exist. Update its status after the next repair pass without losing the original requirements.

## Suggested next pass

Fix visit allocation, permissions/session lifecycle, and shared data refresh first, with integration regression tests reproducing the failures above. Then address demo isolation, OCR ownership, audit consistency, and persistence failure handling. Finish evidence/application workflows before continuing with the agreed standalone hardware tests and integration.
